# Пояснительная записка к техническому проекту

## автоматизированной системы учёта личных расходов «Expenses»

Разработана по структуре, принятой для описания технического проекта АС
(ГОСТ 34.201-89, РД 50-34.698-90): описание автоматизируемых функций, структуры
системы, информационного, программного и технического обеспечения.

---

## 1. Описание автоматизируемых функций

Система автоматизирует полный цикл учёта личной траты: **фиксация** (одним из трёх
способов ввода) → **хранение** (единая база на сервере) → **обработка**
(автоматическая категоризация, синхронизация между устройствами) → **представление**
(списки, диаграммы, экспорт). До внедрения системы эти шаги выполнялись бы вручную и
не были бы согласованы между устройствами.

## 2. Структура системы

### 2.1. Общая схема

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Android    │   │ Telegram    │   │  Браузер    │
│  (Retrofit) │   │  (long-poll)│   │  (fetch)    │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ HTTPS + токен   │ Bot API         │ HTTPS + токен
       └─────────────────┼─────────────────┘
                          ▼
               ┌────────────────────┐
               │   Ktor-бэкенд      │  REST API + Telegram-бот + веб-страница
               │  (один процесс)    │  (одна и та же программа на Kotlin)
               └─────────┬──────────┘
                         │ Exposed (SQL)
                         ▼
                  ┌────────────┐
                  │ PostgreSQL │
                  └────────────┘
```

Принципиальное архитектурное решение: **бот — не база данных, а такой же клиент, как
приложение**. Оба клиента общаются только с бэкендом; бэкенд — единственный, кто
трогает базу данных. Это гарантирует, что данные, введённые через один канал, видны
через все остальные без дополнительной синхронизации между клиентами напрямую.

### 2.2. Компоненты

| Компонент | Технология | Роль |
|---|---|---|
| Бэкенд | Kotlin, Ktor 3.0.3, Netty | REST API, Telegram-бот (long-polling), отдача веб-страницы — один процесс |
| База данных | PostgreSQL 16, доступ через Exposed | Единый источник истины |
| Android-клиент | Kotlin, Jetpack Compose, Retrofit, Room | Мобильный интерфейс с офлайн-кэшем |
| Веб-клиент | HTML/CSS/JS без сборки, отдаётся самим бэкендом | Форма, список, аналитика в браузере |
| Классификатор | Внешний ИИ-сервис Groq (HTTP API) | Обобщённая категория по описанию траты |

### 2.3. Взаимодействие компонентов (протокол)

Обмен данными — REST API поверх HTTPS, формат — JSON (kotlinx.serialization).
Авторизация — bearer-токен в заголовке `Authorization`; токен выдаётся при регистрации
аккаунта и однозначно определяет пользователя (изоляция данных между аккаунтами на
уровне каждого SQL-запроса — фильтр по `user_id`).

**Основные эндпоинты API:**

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Проверка живости сервера |
| `POST /api/register` | Регистрация нового аккаунта, выдача токена |
| `GET /api/me` | Данные текущего аккаунта |
| `GET /api/expenses` | Список трат (с фильтрами по периоду/тегу) |
| `POST /api/expenses` | Добавление траты (идемпотентно по `id`) |
| `PUT /api/expenses/{id}` | Правка траты |
| `DELETE /api/expenses/{id}` | Удаление траты (мягкое) |
| `GET /api/expenses/changes?since=` | Синхронизация по дельте (для офлайн-клиентов) |
| `GET /api/expenses.csv` | Экспорт в CSV |
| `GET /api/budget`, `PUT /api/budget` | Месячный бюджет пользователя |
| `POST /api/reclassify` | Запуск фоновой ИИ-категоризации трат без категории |

Приём сообщений от Telegram — long-polling (бэкенд сам опрашивает Telegram Bot API);
рассматривался вариант webhook, отложен в бэклог как менее необходимый для нагрузки
проекта (см. `docs/architecture.md`).

## 3. Информационное обеспечение (структура данных)

База данных — одна логическая область из трёх таблиц (без внешних ключей — сознательное
упрощение для небольшой схемы, подробное обоснование в `docs/architecture.md` §8).

### 3.1. Таблица `users` — аккаунты

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID, PK | Идентификатор аккаунта |
| `token` | VARCHAR(64), уникальный | Токен доступа (передаётся в `Authorization`) |
| `display_name` | VARCHAR(100) | Отображаемое имя |
| `telegram_id` | BIGINT, уникальный, nullable | Привязанный Telegram-аккаунт (команда `/link`) |
| `monthly_budget` | DECIMAL(12,2), nullable | Месячный лимит расходов |
| `created_at` | TIMESTAMP | Дата создания аккаунта |

### 3.2. Таблица `expenses` — траты

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID, PK | Идентификатор траты (генерируется клиентом — основа идемпотентности) |
| `user_id` | UUID, nullable | Владелец траты (nullable — ради миграции старых строк) |
| `amount` | DECIMAL(12,2) | Сумма |
| `category` | VARCHAR(50) | Категория, как ввёл пользователь («кофе», «такси») |
| `category_group` | VARCHAR(50), nullable | Обобщённая категория, проставляет ИИ в фоне |
| `note` | VARCHAR(255), nullable | Свободная заметка |
| `tag` | VARCHAR(50), nullable | Свободный тег для фильтрации |
| `created_at` | TIMESTAMP | Момент создания |
| `updated_at` | TIMESTAMP | Момент последнего изменения — основа синхронизации по дельте |
| `deleted_at` | TIMESTAMP, nullable | Момент мягкого удаления; `NULL` — запись активна |

### 3.3. Таблица `settings` — настройки (ключ → значение)

| Поле | Тип | Описание |
|---|---|---|
| `key` | VARCHAR(64), PK | Имя настройки |
| `value` | VARCHAR(255) | Значение (хранится строкой, чтобы подходило под любые будущие настройки) |

### 3.4. Схема данных (ER, упрощённо)

```
users (1) ──────── (N) expenses
  id                  user_id → users.id
  token
  telegram_id
  monthly_budget
```

Связь `users` → `expenses` логическая (без объявленного `FOREIGN KEY` в СУБД) —
изоляция и целостность данных обеспечиваются на уровне прикладного кода (каждый
запрос к `expenses` фильтруется по `user_id` текущего аутентифицированного пользователя).

## 4. Программное обеспечение

- **Язык и платформа сервера:** Kotlin 2.1.0 на JVM (Java 21).
- **Веб-фреймворк:** Ktor 3.0.3 (движок Netty).
- **Доступ к БД:** Exposed (Kotlin-обёртка над SQL от JetBrains), пул соединений HikariCP.
- **Формат обмена данными:** kotlinx.serialization (JSON).
- **Общий контракт:** отдельный Gradle-модуль `shared/` с DTO, подключаемый и
  бэкендом, и Android-приложением (`includeBuild`) — исключает рассинхронизацию полей
  между клиентом и сервером на уровне компиляции.
- **Android-клиент:** Jetpack Compose (Material 3), Retrofit (HTTP), Room (локальный
  офлайн-кэш с очередью несинхронизированных изменений).
- **ИИ-категоризация:** запрос к Groq (OpenAI-совместимый chat completions API),
  модель обязана вернуть одно слово из фиксированного списка категорий — упрощает
  разбор ответа и делает аналитику единообразной.

## 5. Техническое обеспечение

Сервер — один VPS (виртуальный выделенный сервер) под Ubuntu Linux. Бэкенд запущен
как процесс `systemd` (не в контейнере — только PostgreSQL контейнеризована через
Docker) и слушает исключительно `127.0.0.1:8080`; наружу его отдаёт nginx,
терминирующий HTTPS (сертификат Let's Encrypt, автопродление через `certbot.timer`).
Подробная и актуальная фактическая схема развёртывания — «Руководство администратора»
и `docs/deploy.md`.

## 6. Организационное обеспечение

Учебный проект с одним исполнителем совмещает роли разработчика и администратора.
В многопользовательском смысле (роли внутри самой системы) выделены:

- **Пользователь** — вводит траты через один из трёх клиентов, видит только свои данные.
- **Администратор** — разворачивает и обслуживает сервер (обновление версии,
  резервное копирование, мониторинг работоспособности).

## 7. Обоснование принятых решений (сводно)

Подробные обоснования каждого решения — в `docs/architecture.md` (раздел «План
улучшений»); здесь — сводка ключевых:

- **Один тег вместо many-to-many.** У траты пользователь вручную вписывает один
  короткий ярлык — плоская колонка проще для фильтрации и миграции, чем отдельная
  связывающая таблица, при той же практической пользе.
- **Мягкое удаление вместо физического.** Офлайн-клиент, не видевший удаления, иначе
  «воскресил» бы трату при следующей синхронизации.
- **Идемпотентность через клиентский UUID.** Повторная отправка того же запроса (из-за
  разрыва сети на мобильном клиенте) не создаёт дубликат.
- **Свой Ktor-бэкенд, а не готовая платформа (Firebase/Supabase).** Цель — практика
  построения серверной части, а не только использования чужой инфраструктуры.
