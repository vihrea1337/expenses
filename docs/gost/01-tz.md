# Техническое задание

## на разработку автоматизированной системы учёта личных расходов «Expenses»

Разработано в соответствии со структурой ГОСТ 34.602-89 «Техническое задание на
создание автоматизированной системы».

---

## 1. Общие сведения

**1.1. Полное наименование системы.** Автоматизированная система учёта личных расходов
«Expenses» (далее — Система).

**1.2. Шифр темы.** Курсовая работа по дисциплине «Проектирование информационных систем»
(клиент-серверная модель приложения/сервиса).

**1.3. Разработчик.** Один разработчик (студент), роль технического исполнителя всех
компонентов — от бэкенда до мобильного клиента.

**1.4. Заказчик (пользователь) системы.** Физическое лицо — сам разработчик, ведущий
личный учёт расходов; система рассчитана на нескольких независимых пользователей
(мультиаккаунтность), но не является коммерческим продуктом.

**1.5. Плановые сроки начала и окончания работ.** Разработка ведётся срезами (итерациями);
базовый срез — 2026-07; текущая развёрнутая версия — v1.1.1 (2026-09).

**1.6. Порядок оформления и предъявления заказчику результатов работ.** Результат
считается принятым, если развёрнутая система отвечает на `GET /health` кодом 200,
все три клиента (Android, Telegram-бот, веб-страница) видят общие данные, а тесты
(бэкенд и Android) проходят в CI.

## 2. Назначение и цели создания системы

**2.1. Назначение системы.** Система предназначена для быстрой фиксации трат из
нескольких мест ввода (мобильное приложение, Telegram-бот, браузер) с единым хранением
данных на сервере и последующей аналитикой (по категориям, по времени, относительно
месячного бюджета).

**2.2. Цели создания системы.**
- Продемонстрировать полноценную клиент-серверную архитектуру: несколько независимых
  клиентов взаимодействуют с одним сервером по общему протоколу (REST API), а не
  хранят каждый свою копию данных.
- Убрать трение при вводе траты: запись должна занимать не больше действия, чем
  сообщение в мессенджере («кофе 200»).
- Дать пользователю единую картину расходов независимо от того, каким клиентом он
  вносил трату.

## 3. Характеристика объекта автоматизации

Объект автоматизации — процесс ручного учёта личных расходов, который до внедрения
системы вёлся бы вручную (блокнот, таблица) и не был бы доступен одновременно с
телефона и из мессенджера. Система заменяет этот процесс электронным учётом с единой
базой данных и автоматической категоризацией.

## 4. Требования к системе

### 4.1. Требования к системе в целом

- **Требования к структуре и функционированию.** Клиент-серверная архитектура: один
  серверный процесс (бэкенд) обслуживает несколько независимых клиентов через общий
  REST API; сервер — единственный источник истины для данных.
- **Требования к численности и квалификации персонала.** Обслуживание системы не
  требует отдельного персонала — администрирование выполняет владелец системы
  (разворачивание, обновление, резервное копирование по инструкции, см.
  «Руководство администратора»).
- **Показатели назначения.** Время ответа сервера на бытовую нагрузку (десятки —
  сотни запросов в сутки от одного-нескольких пользователей) — не критично; система
  не проектировалась под промышленную нагрузку.
- **Требования к надёжности.** Мягкое удаление данных (записи не стираются физически
  сразу — избегается случайная потеря); идемпотентность добавления траты (повторная
  отправка того же запроса не создаёт дубликат — важно для мобильного клиента при
  нестабильной сети); автоматический перезапуск серверного процесса при сбое
  (`systemd`, `Restart=on-failure`).
- **Требования к безопасности.** Доступ к API закрыт bearer-токеном (токен = аккаунт,
  данные разных пользователей изолированы); канал — HTTPS (TLS, сертификат
  Let's Encrypt); сервер слушает только localhost, наружу отдаёт reverse-proxy (nginx).
- **Требования к эргономике и технической эстетике.** Ввод трата на естественном
  языке («такси до дома 350») — не требует заполнения формы для базового сценария.

### 4.2. Требования к функциям (задачам)

| Функция | Описание |
|---|---|
| Быстрый ввод траты | Разбор строки вида «описание сумма» на сумму и категорию |
| Хранение и выдача трат | CRUD-операции с записями, привязанными к аккаунту |
| Синхронизация по дельте | Отдача изменений с определённого момента (для офлайн-клиентов) |
| Мягкое удаление | Удалённые записи помечаются, а не стираются немедленно |
| Автоматическая категоризация | Определение обобщённой категории тратой через внешний ИИ-сервис |
| Аналитика | Диаграмма по категориям, график по времени, фильтр по периоду и тегу |
| Бюджетирование | Месячный лимит расходов с индикатором остатка |
| Экспорт | Выгрузка всех трат в CSV |
| Многопользовательский доступ | Регистрация аккаунта, привязка Telegram-аккаунта к аккаунту приложения |

### 4.3. Требования к видам обеспечения

- **Техническое обеспечение.** Один сервер (VPS) с публичным IP-адресом, доступный по
  SSH; минимальные требования — способность запустить JVM-процесс и контейнер
  PostgreSQL (на практике — от ~1 ГБ ОЗУ и нескольких сотен МБ дискового пространства
  сверх операционной системы).
- **Программное обеспечение.** Сервер: Linux (Ubuntu), Java 21 (JRE), Docker
  (для PostgreSQL), nginx, certbot. Клиенты: Android 8+ (Jetpack Compose), любой
  современный браузер, клиент Telegram.
- **Информационное обеспечение.** Реляционная СУБД PostgreSQL; структура данных —
  см. «Пояснительная записка», раздел «Информационное обеспечение».
- **Лингвистическое обеспечение.** Интерфейс и документация — русский язык; протокол
  обмена данными — JSON (кодировка UTF-8).
- **Организационное обеспечение.** Роли: пользователь (вводит и просматривает свои
  траты), администратор (разворачивает и поддерживает сервер) — в учебном проекте обе
  роли выполняет один человек.

## 5. Состав и содержание работ по созданию системы

Разработка ведётся итеративно, срезами (тонкими сквозными функциями, каждая — от
входа до сохранения в БД и отображения во всех клиентах):

1. Срез 0 — базовый каркас: сервер, домен, сертификат, эндпоинт проверки живости.
2. Срез 1 — одна трата целиком: таблица в БД, добавление и список через API, бот,
   экран в приложении.
3. Развитие (v1.0 → v1.1): авторизация и мультипользовательские аккаунты,
   веб-интерфейс, аналитика, бюджет, ИИ-категоризация, экспорт CSV, офлайн-режим
   в приложении с синхронизацией по дельте, теги, автоматическая очистка старых
   удалённых записей.
4. Перенос на новый сервер (эксплуатационный этап) — см. «Руководство администратора».

## 6. Порядок контроля и приёмки системы

Контроль осуществляется автоматизированными тестами (модульные и интеграционные тесты
бэкенда на движке H2, тесты Android на Robolectric и чистые JVM-тесты бизнес-логики),
запускаемыми в CI при каждом изменении, и ручной проверкой развёрнутой системы: запрос
`/health`, добавление тестовой траты через все три клиента, проверка появления записи
во всех остальных клиентах.

## 7. Требования к составу и содержанию работ по подготовке объекта к вводу системы в действие

- Приобретение и настройка VPS с публичным IP.
- Регистрация домена (использован бесплатный DuckDNS) и настройка DNS-записи на IP сервера.
- Регистрация Telegram-бота через @BotFather для получения токена.
- Получение ключа стороннего ИИ-сервиса (Groq) для функции автоматической категоризации
  (необязательно — без ключа система работает, но без этой функции).

## 9. Источники разработки

Проект разработан по инициативе автора как учебный (курсовой) и портфолио-проект;
архитектурные решения опираются на общепринятую практику построения клиент-серверных
систем (REST API, реляционная СУБД, разделение слоёв представления и данных).
