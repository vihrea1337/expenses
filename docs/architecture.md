# Архитектура проекта Expenses

Документ описывает **что** мы строим, **как** оно устроено и **почему** приняты именно такие решения. Термины расшифрованы; в конце — глоссарий.

---

## 1. Идея продукта
Учёт личных расходов **быстрым вводом**. Главная ценность — минимум трения: не надо открывать приложение, чтобы записать трату, — достаточно строчки в Telegram («кофе 200»). При этом есть и полноценное Android-приложение. Оба входа пишут в **общие данные**.

## 2. Главный архитектурный принцип
> Как только данные заносятся из ДВУХ мест (телефон + бот) и должны быть видны в обоих — им нужен **один общий источник правды, и живёт он на сервере, а не на телефоне.**

Это отличает Expenses от проекта SkyCast, где источником правды был сам телефон (offline-кэш). Здесь так нельзя: телефон не знает, что ты ввёл через бота, пока данные не сведены в одном месте на сервере.

Важное уточнение: **бот — это не база данных.** Бот — просто ещё один клиент Telegram, как и приложение. Поэтому схема не «приложение ← бот», а «приложение ↔ **общий бэкенд** ↔ бот». Причём бот и API для приложения — это **одна и та же программа на Kotlin**.

## 3. Схема
```
  ┌───────────────┐                 ┌──────────────────────────────┐         ┌────────────┐
  │  Android-app  │ ── REST API ──► │      Бэкенд на Kotlin (Ktor) │ ── SQL ─►│ PostgreSQL │
  │ Compose       │ ◄────────────── │  = Telegram-бот              │ ◄────── │  (данные)  │
  │ (+Room-кэш)   │                 │  + HTTP API для приложения   │         └────────────┘
  └───────────────┘                 └───────────────┬──────────────┘
                                                     │ Telegram Bot API
                                                     ▼
                                              ┌────────────┐
                                              │  Telegram  │ ◄─ пользователь пишет «кофе 200»
                                              └────────────┘
```
И бот, и приложение — просто **клиенты**. Данными владеет бэкенд.

## 4. Компоненты
- **backend/ (Ktor)** — сервер на Kotlin. Один процесс делает две вещи:
  1. принимает обновления от Telegram (логика бота);
  2. отдаёт REST API для Android-приложения.
  Оба пишут/читают общую БД.
- **PostgreSQL** — база данных (единый источник правды). Доступ из Kotlin — через **Exposed** (библиотека, позволяет писать запросы на Kotlin, а не голым SQL).
- **androidApp/ (Compose)** — Android-приложение; ходит в API бэкенда (Retrofit). Позже добавим локальный Room-кэш для офлайна.
- **Telegram** — канал быстрого ввода; общается с бэкендом по webhook.

## 5. Стек и версии (и почему)
| Что | Выбор | Почему |
|---|---|---|
| Язык сервера | Kotlin | тот же язык, что учит пользователь; не бросаем Android-навык |
| Веб-фреймворк | **Ktor 3.0.3** | родной для Kotlin, лёгкий; плагин умеет собирать фэт-джар |
| Сборка | Gradle 8.14.3 (wrapper) | wrapper скопирован из WeatherApp; отдельно ставить Gradle не нужно |
| JDK | 21 (JBR из Android Studio) | уже стоит на машине; отдельная установка не требуется |
| Kotlin | 2.1.0 | стабильная, совместима с Ktor 3.0.3 |
| БД | PostgreSQL | «взрослая» реляционная СУБД; хороший опыт для резюме |
| Доступ к БД | Exposed | Kotlin-обёртка над SQL от JetBrains |
| JSON | kotlinx.serialization | пользователь уже знает по SkyCast |
| Авторизация приложения | bearer-токен | простой и достаточный способ доказать «это я» |

Развилки, которые уже приняты: **свой бэкенд на Ktor** (а не готовый Firebase/Supabase) — чтобы учить бэкенд; **webhook** (а не long-polling) в проде — эффективнее, и у пользователя есть VPS с публичным адресом.

## 6. Инфраструктура (деплой)
На VPS пользователя **уже** работают его сайт и VPN за **nginx на порту 443**. Порт 443 занят — но отдельный порт нам и не нужен.

**Решение: добавить поддомен в существующий nginx.** nginx умеет виртуальные хосты — на один IP и порт 443 вешается много сервисов, а nginx направляет запрос по имени домена (механизм SNI / заголовок Host). Значит:
1. Заводим поддомен, например `bot.<домен>` (или бесплатный на DuckDNS), направленный на IP VPS.
2. Ktor слушает **внутренний** `127.0.0.1:8080` — наружу не торчит.
3. В nginx добавляем блок, который принимает HTTPS для поддомена и **проксирует** запросы в Ktor:
```nginx
server {
    listen 443 ssl;
    server_name bot.<домен>;

    ssl_certificate     /etc/letsencrypt/live/bot.<домен>/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/bot.<домен>/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
    }
}
```
4. Сертификат для поддомена — бесплатно через **certbot** (Let's Encrypt).
5. Круглосуточную работу обеспечивает **systemd-юнит** (Linux-служба): запускает фэт-джар, перезапускает после сбоя/перезагрузки.

**И webhook бота, и API приложения** — это разные «ручки» одного Ktor за этим nginx:
- Telegram шлёт обновления на `https://bot.<домен>/telegram/<секрет>`
- приложение ходит на `https://bot.<домен>/api/...`

Приём обновлений от Telegram:
- **в проде — webhook** (Telegram сам стучится на наш адрес);
- **локально при разработке — long-polling** (бот сам опрашивает Telegram) или туннель `ngrok`/`cloudflared`, потому что у ноутбука нет публичного адреса. Код бота один и тот же — меняется только «способ доставки обновлений» (заложим переключаемым).

Запасной вариант, если поддомен не подойдёт: Telegram разрешает webhook на портах **443, 80, 88, 8443** — можно поднять отдельного слушателя на `8443`. Но поддомен через существующий nginx чище.

**Caddy НЕ используем** (хоть он и удобен автосертификатами) — он бы подрался с nginx за порт 443.

## 7. Безопасность
- **Ktor слушает только `127.0.0.1`** — из интернета недоступен, до него дотягивается лишь локальный nginx.
- **Секрет webhook.** При регистрации webhook задаём `secret_token`; Telegram присылает его в заголовке каждого запроса. Бэкенд отклоняет запрос без правильного секрета (адрес публичный — иначе кто угодно слал бы фейковые «сообщения»).
- **Авторизация приложения** — bearer-токен (строка-пропуск в заголовке запроса), чтобы данные были приватными.
- **Привязка аккаунтов** (планово). Как бэкенд поймёт, что траты из бота — «твои», и покажет их в «твоём» приложении: приложение показывает код привязки → пользователь отправляет его боту → бэкенд связывает Telegram-аккаунт с аккаунтом в приложении.
- **Секреты не коммитим.** Токен бота, пароль БД, секрет webhook — только в переменных окружения / незакоммиченных файлах (см. `.gitignore`).

## 8. План улучшений (после базового каркаса)
По важности:
1. **Ядро:** общий бэкенд+БД (есть каркас) · привязка аккаунтов · авторизация · ✅ **UUID + идемпотентность** (2026-09-02: у каждой траты уникальный id, назначает его клиент; повтор с тем же id не создаёт дубль — см. `ExpenseRepository.add`) · ✅ **общий Kotlin-модуль моделей** (2026-09-02: `shared/`, по образцу devlog — см. ниже).
2. **Сверху:** 🟨 офлайн-first в приложении (2026-09-02: базовая часть сделана, см. ниже) +
   двусторонняя синхронизация (`updated_at`, побеждает более свежая запись — **не сделано**,
   нужна миграция схемы) · умный парсер ввода «кофе 200» → категория+сумма (**одна логика на
   сервере**, чтобы бот и приложение считали одинаково) · реалтайм (бот добавил → телефон
   обновился: FCM-push или polling).
3. **Фичи:** бюджеты/лимиты, теги, повторяющиеся траты, несколько валют, экспорт в CSV, графики.

### Офлайн-first в Android-приложении (текущее состояние, 2026-09-02)
Локальный кэш — Room (`androidApp/.../data/local`: `ExpenseEntity`, `ExpenseDao`,
`ExpensesDatabase`). Экран **всегда** читает список трат из кэша (`Flow`), а не напрямую из
сети — работает офлайн и обновляется реактивно. Добавление трат — оптимистичное: новая
трата с id, придуманным на телефоне (`UUID`), сразу попадает в Room (`synced = false`) и
видна на экране; отправка на сервер идёт фоном при каждой синхронизации, используя уже
реализованную идемпотентность (тот же id → сервер не создаёт дубль при повторной отправке).

Синхронизация сейчас — **не дельта-протокол**: `ExpensesRepository.sync()` тянет **весь**
список (`GET /api/expenses`) и перезаписывает подтверждённые строки кэша, не трогая ещё не
отправленные. Это по факту "сервер побеждает" для всего, что он уже принял — работает и
достаточно для одного активного устройства, но НЕ решает конфликт, если один и тот же
пользователь правит одну трату одновременно с двух устройств (частый сценарий синхронизации
из §8, ради которого задумывался `updated_at`).

Почему не сделано целиком за один заход: полноценный `GET /api/expenses/changes?since=` (по
аналогии с devlog) и разрешение конфликтов по `updated_at` требуют миграции схемы — в таблице
`expenses` сейчас есть только `created_at`, колонки `updated_at` и мягкого удаления
(`deleted_at`) нет вовсе. Добавлять их впопыхах рискованно: это ломает семантику
`DELETE /api/expenses/{id}` (сейчас — настоящее удаление строки, а тогда нужно превратить в
пометку), а `GET /api/expenses`, `expenses.csv` и переклассификация ИИ тоже читают эту
таблицу и должны научиться игнорировать помеченные удалёнными записи. Следующий заход: 1)
миграция (`updated_at` на каждую запись/правку, `deleted_at` на удаление, soft-delete вместо
`DELETE`), 2) `GET /api/expenses/changes?since=&limit=` → `{expenses, serverTime, hasMore}`
(добавить `deleted: Boolean = false` в `Expense` из `shared/`), 3) Android-клиент запрашивает
дельту вместо полного списка и мержит по `updated_at`, 4) офлайн-редактирование/удаление
(сейчас требуют сети напрямую — сознательно не покрыты, встречаются реже добавления).

Тесты (Robolectric, JVM, без эмулятора/телефона) — `ExpenseDaoTest`: upsert-идемпотентность
локальной строки, фильтрация несинхронизированных, и главное — `pruneMissing` не удаляет
несинхронизированные траты, даже если сервер о них ещё не знает.

### Общий модуль моделей (`shared/`)
Контракт API (DTO трат, бюджета, регистрации) раньше был описан дважды — на бэкенде и в
Android-приложении; несовпадение полей превращалось из ошибки компиляции в молчаливый баг
в рантайме. Теперь это отдельный Gradle-проект `shared/` (Kotlin/JVM, JVM-байткод 17 — чтобы
его читал и Android, и бэкенд на JDK 21), подключается к обеим сборкам через `includeBuild`,
без версии в Maven-смысле — просто как соседний модуль. Пакет тот же, что у бэкенда
(`io.github.vihrea1337.expenses`), поэтому серверному коду не нужно ничего импортировать;
Android-приложение импортирует явно. Контрактные тесты (имена полей в JSON, обратная
совместимость со старым клиентом) — в `shared/src/test`.

Веб-страница (`backend/src/main/resources/static/index.html`) в этот модуль **не переведена**
осознанно: она чистый JS без сборки, TypeScript/Kotlin-модуль ей просто негде было бы
скомпилировать без появления в проекте фронтенд-тулчейна — непропорциональная цена для
нескольких полей.

## Глоссарий
- **API** — «дверца» для запросов к серверу; набор адресов-ручек, на которые можно послать запрос и получить данные.
- **REST API / эндпоинт** — стиль API поверх HTTP; эндпоинт — конкретный адрес-ручка (например, `/api/expenses`).
- **Бэкенд** — серверная часть: программа, работающая круглосуточно на удалённом компьютере и отвечающая на запросы.
- **Ktor** — Kotlin-фреймворк для написания серверов (и клиентов).
- **Netty** — «мотор» HTTP-сервера внутри Ktor, принимает сетевые соединения.
- **Фэт-джар (fat jar)** — один `.jar`-файл, внутри которого и твой код, и все библиотеки; удобно запускать на сервере одной командой.
- **PostgreSQL** — реляционная база данных (таблицы, SQL).
- **Exposed** — Kotlin-библиотека для работы с БД: запросы пишутся на Kotlin.
- **kotlinx.serialization** — превращает Kotlin-классы в JSON и обратно.
- **webhook** — Telegram сам присылает POST-запрос на наш публичный адрес при каждом сообщении.
- **long-polling** — наоборот: наш бот сам периодически спрашивает Telegram, нет ли новых сообщений.
- **reverse proxy** — «привратник» (nginx) перед приложением: принимает внешние запросы, расшифровывает HTTPS и передаёт их внутрь.
- **TLS/SSL, сертификат** — шифрование канала (`https`); сертификат — «паспорт» домена, подтверждающий подлинность.
- **certbot / Let's Encrypt** — бесплатная автоматическая выдача и продление сертификатов.
- **systemd** — менеджер служб в Linux; следит, чтобы программа работала постоянно и перезапускалась.
- **bearer-токен** — секретная строка-пропуск в заголовке запроса, доказывающая, кто его шлёт.
- **идемпотентность** — повторная отправка того же запроса не создаёт дубликат.
- **FCM** — сервис Google для доставки push-уведомлений на телефон.
- **SNI** — механизм, по которому сервер понимает, к какому домену обращается клиент (позволяет одному порту 443 обслуживать много сайтов).
